Word Prediction

What powers next-word suggestions in shipping keyboards, and what phonekeeb should build. All local numbers are measured against this repo's real 3000-word vocabularies.

how

do you much are are you

The goal. Top bigram successors of "how" plus one chained two-word chip, from tables built for this note (OpenSubtitles 2018). Today the strip is blank until the first letter of the next word.

  • No shipping keyboard runs a large model in the strip. Gboard uses a 1.4 MB LSTM, Apple a ~34M transformer, SwiftKey a neural + n-gram blend. Large models only serve slow features like proofread.
  • Bigram tables cost ~37 KB gzipped per language and raise measured next-word hit@3 from 12% to 23%. A lazy trigram layer (~0.8 MB) reaches 33%.
  • Corpus register beats model machinery. Subtitle bigrams outscore web bigrams by 30% relative on the same test, and their chips read like chat, not like web boilerplate.
  • Bug found on the way: "i" and "a" are missing from words-en.js. Fix before any model work.

What the suggestion strip runs on, 2026

Every vendor splits the work the same way. A small on-device model answers inside roughly 20 ms per keystroke. A big model handles optional, slower features. The strip itself never waits for an LLM.

Google Gboard

FST decoder + n-gram LM · 1.4 MB federated LSTM for next-word

The decoder is a finite-state pipeline with a 5 to 10 MB language model budget. Next-word chips come from a 1.4M-parameter LSTM trained by federated learning with differential privacy. A 2024 paper swaps the n-gram inside the decoder for a small neural LM. Gemini Nano only powers proofread and rewrite.

Apple, stock keyboard

GPT-2-style transformer · 6 blocks · ~34M params · per keystroke

iOS 17 rebuilt autocorrect and inline predictions on this on-device model. Third-party keyboards get none of it; public APIs stop at prefix completion and the user lexicon. iOS 26 adds a system-hosted ~3B model (Foundation Models) that keyboard extensions can call, at phrase-level speed only.

Microsoft SwiftKey

static neural net + dynamic n-gram user model

Both models run side by side and compete for each suggestion slot. The n-gram side learns the user's own phrases. Two-word chips shipped in SwiftKey 6.0. Copilot features are a separate cloud call.

8pen shipped no prediction at all, and its successor 8VIM still has none. A working context model is a clear, deliberate divergence in phonekeeb's favor.

Register beats machinery

Two bigram sources were scored head to head on the same subtitle test set. The web-corpus table is not merely weaker, its chips read wrong for a chat keyboard.

OpenSubtitles is also the corpus behind the existing word lists, so one corpus and one attribution line covers everything. Head coverage of our vocabularies: 99.9% English, 100% Czech. Czech alternatives fail on licenses: the national corpus is academic-use, Leipzig carries a non-commercial risk.

The vocabulary bug

⚠ FIX BEFORE ANY MODEL WORK

Both word lists were generated with a minimum word length of 2, so "i" and "a" are missing from words-en.js. The generation also split on apostrophes and kept fragments like didn, re, ll. The bigram data then learns you → re. Fix the regeneration filter: allow length 1 and keep apostrophes inside words, so don't is one entry. Strip apostrophes in the match key so a gesture-typed dont still finds it.

Recommended build order

  1. Regenerate the word lists with the filter fix above.
  2. Build script (tools/build-ngrams.py): one streaming pass over the OpenSubtitles dump, keep pairs where both words are in the vocabulary, prune to top-5 successors, emit bigrams-en.js / bigrams-cs.js as rank-ordered word lists. A partial 80 MB download already produced all numbers above.
  3. Extend the predictor to predict(prefix, prevWords, limit): walk trigram, then bigram, then unigram lists, deduplicate, filter by prefix. An empty prefix now returns next-word chips. The call site passes the last words of typedText.
  4. Two-word chips: chain the rank-1 successor of a top candidate and show it as an extra chip ("are you" next to "are"). A wrong chain costs a strip slot, never a wrong insert.
  5. Personal model: count the user's committed bigrams in localStorage with per-session decay, promote candidates past a threshold.
  6. Eval harness (tools/eval-prediction.mjs): hit@1 / hit@3 on a held-out subtitle slice, run before and after each model change.
  7. Trigram layer when wanted: same script, contexts with count ≥ 20, lazy-loaded after first paint. Superseded 2026-08-25: a words-only table cannot rerank prefix completions. The trigram layer ships with counts, as step 3 of the scored design below.

Two UX notes. A gesture letter costs more than a tap, so an accepted chip saves more time here than on a normal keyboard, and the after-space moment is currently blank. And the next-word distribution predicts likely first letters, which can later feed the planned glide-target preview weighting.

Scored prediction design

Added 2026-08-25, from live use. Text "you are ", typed prefix am. The shipped bigram layer offers plain frequency order: am, american, america, amazing, among. SwiftKey offers amazing, am, an. A corpus probe (tools/probe-context-scoring.py, on an 80 MB range download of the dump) confirms the design below reproduces that quality:

you are am

amazing among an and am

Scored order from the probe, measured on the EN OpenSubtitles sample. "an" enters as a typo hypothesis; its count after "you are" beats the edit penalty.

Three mechanisms, one score:

  1. Context reranking. "amazing" is successor rank 141 of "you are" (count 34 of 32,089), so any pruned top-K list misses it. Flip the lookup direction: collect candidates from the typed prefix (a ~3000-word vocabulary scan), then score each by stored counts. Tables therefore need counts and full successor lists, not top 5.
  2. Verbatim guarantee. The literal typed word stays reachable: if no exact-prefix word makes the strip on score, the best one takes the last slot. Corrections stay visible and tappable, never silent.
  3. Typo hypotheses. Candidates also include words whose beginning is within edit distance 1 of the prefix ("an" for "am"). Each edit multiplies the score by a penalty.

The score is stupid backoff (Brants 2007): trigram count over context count when seen, else 0.4 × the bigram probability, else 0.16 × the unigram probability, times 0.05 per edit. All three constants get tuned by the eval harness, then recorded in features.md. Cost: "you are" alone has 978 successors with count ≥ 3, so tables grow well past today's 37 KB. The levers are a per-context count floor, a successor cap, and 1-byte log-quantized counts; expected order is a few hundred KB gzipped for bigrams and 1 to 2 MB for the lazy trigram layer, far under the iOS memory cap.

Agreed order, each step measurable: the eval harness first (constants get tuned, so measurement comes first, with a typo-simulation eval next to hit@3), then bigrams with counts plus the scoring predictor, then the trigram layer with counts behind a flag. Later refinement: gesture-aware edit costs, because this keyboard's typos are crossing-count slips and sector misses, not QWERTY neighbor taps.

iOS port notes

documentContextBeforeInput hands a keyboard extension the text before the cursor (about 300 characters in practice), enough for trigram context. The tables sit far under the 48 to 60 MB extension memory ceiling. The Foundation Models route deserves one prototype spike later; the jKey keyboard already ships it, and the model's memory is system-managed, outside the extension's budget.
