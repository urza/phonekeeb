Apple's on-device model, from inside a keyboard

The roadmap says the iOS route to a big model is the Foundation Models framework. This tests that sentence: what the API hands a keyboard extension, what it refuses, and what it costs. Facts marked apple come from Apple's own pages, forums or shipped docs. 3rd party is weaker.

TL;DR

  • It gives you words, never numbers. No logits, no per-token probability, no lexicon constraint. Both tricks that make lm-predict.py work are impossible through this API.
  • Czech is not supported. Not in the 23 locales of 2025, not in the 25 languages of 2026. That list added Polish, Russian and Ukrainian and still skipped Czech.
  • Memory is free. The OS hosts the model, so it does not count against the extension's Jetsam limit. That is the one real gift, and nothing else we measured has it.
  • Speed puts it where the roadmap already put it. ~30 tokens/s, so one to two seconds per strip. Phrase level. Never per keystroke.
  • The one shipping keyboard that used it removed it. jKey 2026.1 threw the engine away and shipped its own model.
The verdict in one line. Use it as the English arm of roadmap direction 8, where it is free, local and costs no extension memory. It is not an answer for the Czech arm, and Czech is why direction 8 was opened.

The model behind the API

Two generations exist. Third-party apps get the on-device text model. apple

Two architecture details explain the speed. The model splits into two blocks at a 5:3 depth ratio, and block 2 reuses block 1's final-layer KV cache, cutting KV memory by 37.5%. The 2026 model keeps all 20B in NAND flash and swaps routed experts into DRAM per prompt, which is how a 20B model fits a phone at all.

Reverse engineering of the shipped bundle 3rd party adds what Apple does not publish: the text model is AFMTextV7, 3.18B parameters over 56 layers (35 standard, 21 KV-reuse), hidden size 2048, a 153,600-token vocabulary, and about 1.0-1.1 GB on disk. A separate 48.8M draft model does speculative decoding. LoRA adapters are rank 32 across 1,173 attachment points.

Two of those numbers matter to us. 1 GB is what the OS holds for free on our behalf, against an extension budget of 48-60 MB. And 153,600 tokens is six times GPT-2's vocabulary, a real cost for any prefix-constrained decode, if we could do one, which we cannot.

What the API gives

The whole surface, from the documentation shipped with Xcode. apple

sampling accepts .greedy, .random(top:seed:) and .random(probabilityThreshold:seed:). So you pick top-k or top-p, and you can make generation deterministic. You still never see the distribution those options operate on.

Three availability failures, each needing a different response: deviceNotEligible is permanent, fall back forever; appleIntelligenceNotEnabled is a user setting, one prompt is fair; modelNotReady means still downloading, retry quietly. A keyboard must handle all three, because the local engine has to keep working in every one.

What it withholds, and why each one hurts

No logits, no per-token probabilities

no API existsblocks the merge

Our engine merges evidence by weighing scores, and langPosterior() weighs two languages every keystroke. A big model that returns six strings and no scores cannot enter that merge. It can only replace or append. A principled combination becomes a heuristic one.

No lexicon constraint

blocks the prefix maskinvented words

lm-predict.py masks the vocabulary at every beam step to tokens still compatible with the typed letters. That needs the vocabulary. Here you can only write "words beginning with zapla" in the prompt and hope. The LM study already measured the result of no constraint: "smool, smoop, smoola". @Generable fixes the shape of the answer, a list of six strings, and says nothing about whether those strings are words.

Guardrails you do not control

forum 792908moves between betas

Benign prompts draw guardrailViolation, appearing and disappearing across OS betas with no code change. A keyboard types what the user types. A strip that silently empties on some sentences is worse than one that is merely wrong. The Python SDK exposes a permissive guardrail mode, which hints the Swift API has the same escape hatch. Check before building.

No control over the model version

adapters expire

Adapters must be retrained for every new base model. Any tuning we do carries an OS-release-shaped expiry date.

The 4,096-token session window is the one limit that does not bite us. A keyboard sees a sentence.

Availability

Devices

iPhone 15 Pro and newer (A17 Pro and up), Apple silicon Macs, M-series iPads. Everything older gets nothing. jKey named this as one of its three reasons for leaving.

Languages apple

2025 covers 23 locales: English (US, GB, AU), French (FR, CA), German, Italian, Spanish (ES, US, 419), Portuguese (BR, PT), Dutch, Danish, Norwegian, Swedish, Turkish, Vietnamese, Chinese (CN, TW, HK), Japanese, Korean. The 2026 model adds Arabic, Finnish, Hebrew, Hindi, Indonesian, Malay, Polish, Russian, Thai and Ukrainian.

Czech appears in neither list. The 2026 list is the sharper evidence, because it added three Slavic languages and skipped Czech. Read supportedLanguages at runtime rather than trusting a hardcoded list, but plan for absence.

The model is multilingual, so it will emit Czech if pushed. Unsupported means untested and untuned, and czech-lm-research.md is 545 lines of evidence that a model's behavior outside its trained register is not guessable. If this route is ever taken for Czech, measure it on the 14 game cases first, like every other engine in that study.

Europe

Apple Intelligence reached the EU in April 2025 with iOS 18.4, so the framework works here today. The June 2026 newsroom post delays Siri AI in the EU for iOS 27, and its wording is narrow: the conversations app, Visual Intelligence, writing tools, Camera Siri mode, and "other Siri AI capabilities announced at WWDC26". apple It says nothing about the Foundation Models framework, and macOS 27 keeps Siri AI even in the EU.

One third-party summary reads this as the whole framework being absent on EU iPhones at launch. That reading is not supported by Apple's text, and it is not settled either. For a Czech user this is a real risk on the 2026 model and no risk at all on the 2025 one.

Cost: memory, speed, and the rate limit

Memory: effectively zero apple

An Apple Frameworks Engineer confirmed the model and its inference resources are managed centrally by the OS, shared across all Apple Intelligence features, and do not count against the app's Jetsam limit. Multiple sessions in parallel are supported, and run serially on the Neural Engine.

Every local neural option above 100 MB is dead inside a keyboard extension. This one is not, and it is 3B parameters. That is the whole argument for the route.

Speed

Apple published about 30 tokens per second and roughly 0.6 ms time-to-first-token per prompt token on an iPhone 15 Pro for the first generation. apple Third-party testing puts short answers at 30-50 tokens/s, falling when another Neural Engine workload runs. Six candidate words as a structured list is perhaps 30-60 tokens, so one strip is one to two seconds before prompt processing. Our per-keystroke budget is about 20 ms. The gap is two orders of magnitude, the same conclusion the local XL model reached at 2.3 s per strip.

The rate limit is the undocumented risk apple

Apple's engineer states rate limiting applies when the device is on battery and the process runs in the background, and that it surfaces as a misleading "Safety guardrail was triggered after consecutive failures during streaming" error. One developer hit it with four requests at 30-second intervals. Advice given: do not stream in background contexts, use respond instead.

Nobody has answered whether a keyboard extension counts as background. It is visible on screen and it is not the foreground app. A keyboard firing one request per word boundary would sit far above four requests per two minutes. Test on a device before any design depends on it. This may be the real reason jKey found the route slow.

Full Access

No source says whether the framework is reachable from a keyboard extension without Full Access. It is a local XPC service, not network, so it should be. Guideline 4.4.1 requires the keyboard to work fully without Full Access, and our design already meets that. Test it, and treat the answer as a gate.

The one shipping precedent

jKey is an accessible keyboard for VoiceOver users: five large letter clusters, and the keyboard works out the intended word. A harder decoding problem than ours, and the same shape.

Its prediction ran on Apple Intelligence. In jKey 2026.1 the developer replaced it with a language model shipped inside the keyboard, listing three reasons 3rd party:

  • predictions were slow,
  • they only worked on newer devices,
  • they often were not the words users had asked for.

Stated gains after the change: no networking code and no AI service of any kind, so nothing typed can leave the device; the engine works on every supported device; and one engine now drives completion, next-word prediction and sentence capitalization.

That is our architecture, arrived at independently, by the only other keyboard that tried this API for this job. The third reason is the interesting one. It is not about speed or hardware. It says a 3B general model asked in prose for word suggestions returns the wrong words, which is what the LM study measured for every pretrained model at next-word: 10.0 hit@1 for a 124M model against 17.3 for 1.8 MB of counts.

What WWDC 2026 changed

  • Image input. Prompts take images; Vision tools (OCR, barcodes) are callable by the model. Nothing for us.
  • The LanguageModel protocol. Third-party providers ship Swift packages conforming to it. Anthropic and Google shipped implementations on day one. Swap the provider by changing a package dependency; the rest of the app keeps using LanguageModelSession.
  • Free Private Cloud Compute. App Store Small Business Program apps under 2 million lifetime first-time downloads get the server model free. Above that line, no published pricing. Claude and Gemini are metered separately.
  • Dynamic Profiles, an fm CLI, a Python SDK, an evaluations framework, and Instruments profiling for model calls.

The protocol is the piece that matters. Direction 8 decided on 2026-08-27 to run two specialist models, one per language, merged by the posterior we already compute. iOS 27 turns that into one interface with two providers behind it: Apple's local model for English, something else for Czech. The keyboard writes one code path.

The free PCC tier does not solve Czech. The cloud model is the same family and presumably the same language list. And any cloud call is exactly the network dependency fifteen years of SwiftKey reviews say users will not forgive unless it is visibly optional and off by default.

What this means for phonekeeb

Keep direction 8 as written, and split it by language.

The English arm gets a strong answer. Apple's model is free, local, needs no network, costs no extension memory, and reaches quality our tables cannot at phrase level. Cost: one to two seconds, iPhone 15 Pro and newer, and an untested rate limit.
The Czech arm gets no answer here. Czech is unsupported in both generations, and the two game cases that opened direction 8, zaplavat and kuře, are Czech. Options by cost: wait for Czech support and re-measure; route Czech through a provider package at metered cost, off by default; or accept that the Czech arm stays local and capped.

Three things to do before any code

  1. Measure Apple's model on the 14 game cases. The fm CLI and the Python SDK make this the same shape as tools/lm-predict.py, so the harness already exists in outline. It needs a Mac, and ios-deployment-research.md prices a cloud Mac at about 3 EUR per day for a one-day job. Run the English cases as the real test, and the Czech ones to price the unsupported-language question with numbers instead of a language list.
  2. Test the rate limit from a real keyboard extension. One request per word boundary, on battery, for two minutes. If it throttles, the feature is a "think harder" chip and not an automatic second opinion.
  3. Test whether it works without Full Access. Guideline 4.4.1 makes this a gate, not a detail.

One thing not to do

Do not let this route touch the per-keystroke strip. Two orders of magnitude of latency, no probabilities to merge, no lexicon constraint, and a shipping keyboard that already tried and reverted. The 1.3 MB mini model stays the right answer for the strip, and the compounding design still holds: whatever the big model contributes and the user accepts goes into PersonalModel, so the big model teaches the small one and is needed once per new word, ever.
