A big model behind an API, measured

Roadmap direction 8 says a big model should sit beside the small one. A 27B on the user's own network answered our 14 game cases and 400 held-out pairs. It wins the game by one case and loses every measured task.

TL;DR

  • It loses every held-out task, in both languages. Next-word, prefix completion, corrupted prefix. The closest is English next-word, 19.5 against our 22.5.
  • It wins the prediction game, 8 of 14 against 7. The game rewards meaning. The pairs reward frequency. Same split as always, now at 27B.
  • Czech everyday speech is still the hole. 1 of 5 Czech cases. A 1.58B Czech model answers all five.
  • Reasoning is a loss at every price. 160 times the latency, no better score, and two answers lost inside the thinking block.
  • Words without numbers cost more than expected. 17 times bigger than Czech-GPT-2-XL and two game cases behind it, because a chat answer carries no probability and no prefix constraint.
The verdict in one line. Nothing here supports letting a big model rank the strip. Its one win is at phrase level, which is where the roadmap already put it.

The setup

vLLM on the local network, serving unsloth/Qwen3.8-27B-NVFP4. Strip of 6, temperature 0, non-thinking unless a row says otherwise. Harness: tools/api-lm-predict.mjs, any OpenAI-compatible endpoint. The 14 cases live in tools/game-cases.mjs, shared with tools/eval-game.mjs, so the model and the engine answer the same list.

This is the first measurement of a model we can only talk to in words. lm-predict.py uses logits and a constrained beam. Apple's framework gives neither, so this shape is what iOS forces on us.

Next-word is the closest call and still a loss. The roadmap said a big model loses where frequency decides. It does, and 27B does not change it.

Prefix completion is a large loss, which is new. The 124M Czech models won this task. This one loses it by 14 points in English and 28 in Czech. The cause is the interface, not the knowledge: asked for six words starting with fi, it writes six plausible words in no frequency order, and our tables know which one people type.

The corrupted prefix is a collapse. The first run scored 0.5 because the prompt made the typed letters a rule and the model obeyed. The --fuzzy-prefix prompt states the engine's real rule, that a letter can be wrong, and that lifts it only to 3.1. Two letters with one wrong is a job for edit distance over a known lexicon.

Reasoning made it worse

Thinking mode cost 32 s per strip against 0.2 s, and scored no better. At temperature 0 it looped: on the case smoo it wrote 10306 tokens, most of them the line "smoothe" no. repeated, then ended its turn with no answer. Two cases died that way even at the recommended temperature 0.6.

The harness now reports an empty strip as no answer and totals it separately. Counting it as a miss would blame the model's word choice for a fault of the run.

What it changes for direction 8

The direction survives and its shape narrows.

  • A big model is not a better strip. Worse at the per-keystroke job in both languages, and not because of size or Czech.
  • The win is phrase level and meaning level. 8 of 14 against 7 is thin, and it is the only win.
  • The text-only interface costs more than it seemed. Direction 8 assumed candidates the merge weighs by langPosterior(). That needs numbers. A chat model gives an order and nothing else, and this is what an order alone is worth.
  • Reasoning models are the wrong tool here. Use the non-thinking path or a base model.

The open lead: logprobs

This server allows logprobs. vLLM returns the top-N alternatives per generated token on /v1/completions, which is enough to run the same constrained beam lm-predict.py uses locally, against a 27B we could never load here. That would separate the two causes this study confounds: what the model does not know, and what the chat interface throws away. Cheapest next experiment on this hardware, and it needs no new model.
